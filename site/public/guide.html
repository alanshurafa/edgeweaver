    How to read this site

    TLDR

    You do not need repository experience to use this field guide. Repository 101 below defines the basic objects and the exact work loop. Substantive system pages then speak at two depths: Plain for the idea and Technical for reproduction. Plain is the first-visit default; Technical and Both are deliberate choices. Search is local, and three guided tracks serve understanding, technical inspection, and rebuilding.

    Repository 101: what you are looking at

    A repository, often shortened to repo, is a project folder whose changes are recorded by version control. Edgeweaver's repository contains design authority, procedures, programs, templates, evidence, and this website. It does not mean that every file has equal authority, and it never means secrets belong in the recorded history.

    Root
    The repository's top level. Files such as START-HERE.md, PLAN.md, and IMPLEMENTATION.md sit at the root. A path without a parent folder starts there.
    Folder and path
    A folder groups related files. A path is the address from the root to one item, such as scripts/waking/orient.mjs. Slashes mean “inside this folder.” The final part is the file name.
    Tracked, untracked, and ignored
    A tracked file belongs to the recorded project history. An untracked file exists locally but has not been added to that history. An ignored file matches .gitignore, so ordinary Git commands leave it out. Edgeweaver keeps secrets and machine state in ignored locations such as .env.local and state/.
    Clone
    A local copy of a repository and its history. Cloning gives you the files; it does not give you private credentials, ignored state, or authority to close human gates.
    Commit
    A named snapshot of selected tracked changes, with an author and message. A commit is evidence of what changed, not proof that the change was correct. Verification supplies that proof.
    Branch
    A movable line of commits used to develop a change without immediately replacing the main line. In this project, identity proposals use proposal branches. A being never writes canonical soul-repo main.
    Fork
    A separate repository copied from another one, usually under different ownership. A fork is not the same as a branch. Edgeweaver's soul write model lets a being work from a fork and propose changes across repositories.
    Environment variable
    A named value supplied by the operating environment, commonly used for configuration or credentials. Documentation may name a variable, but values stay outside Git and outside this site.
    Terminal and CLI
    A terminal is the text window where commands run. A command-line interface, or CLI, is a program controlled by those commands. The instructions show commands as code blocks; run them from the repository root unless they say otherwise.
    JSON
    A strict data format made of objects, arrays, names, strings, numbers, booleans, and null. Files such as site/src/nav.json are data read by programs, so punctuation and quoted names matter.
    Markdown
    A plain-text writing format used by files ending in .md. Hash marks create headings, backticks mark code, and links remain readable even before rendering.
    Source of truth
    The one authoritative place a fact or configuration is meant to come from. Copies may explain or generate from it, but they must not quietly compete with it. This site explains the repository; it does not outrank the design documents or become a being's identity source.

    The literal Edgeweaver work loop

    The repository is a plan and build system, so reading the right file in the right order matters more than browsing at random. The authority order is: PLAN.md, GROWING-EDGEWEAVER.md, and FAMILY.md for design; then IMPLEMENTATION.md for build status and sequencing; then the matching file under checklists/ for the procedure. If a checklist contradicts higher authority, stop and log the conflict rather than improvising.

    1. Open START-HERE.md. Follow its session protocol, safety rules, and “when stuck” guidance literally.
    2. Read the IMPLEMENTATION.md status ledger. Find the first applicable unticked step. Do not drive construction from the broad design plan.
    3. Open the matching checklist. Read the current step and its prerequisites. A line beginning STOP is a human gate, not a suggestion.
    4. Do one step. Keep the change within the named files and preserve unrelated work already in the tree.
    5. Run the stated verification. Report a failure as a failure. Never tick or claim a check you did not run.
    6. Record and commit the verified result. Stage only intended files, use the repository's commit convention, and push at the session boundary when the runbook authorizes it.

    Secrets never enter this loop. Values live only in ignored local state or approved external custody. The gates repository never receives a runtime credential. Identity is canonical only in each being's own soul repository.

    Two languages on substantive pages

    Each concept and being page keeps the same six-part skeleton: TLDR, In plain words, How it works, Where it lives in the repo, dated status, and genuine uncertainty. Plain assumes no technical background. Technical names exact paths, functions, schemas, invariants, and failure modes. The two sections are adjacent in the source so they cannot drift into separate documents.

    With JavaScript, Plain, Technical, or Both changes what is visible. Plain is the initial choice for a first-time visitor. A deliberate choice of Technical or Both persists on that device. The current choice also appears in every page URL as ?view=plain, ?view=technical, or ?view=both; an explicit shared URL overrides the saved preference. Links into hidden detail do not reveal it automatically, and Plain search excludes technical-register results. Status, uncertainty, honesty, and repo-location sections are outside the lens. Without JavaScript and in print, both registers remain available.

    Track three: reproduce the method

    Read the honesty boundary, then follow the reproduction guide as standing orders. If you are new to this work, the guided walkthrough paces the same orders step by step, with copy-ready agent prompts and explicit human-only stops. The guide distinguishes what an agent can build from what a human must author, witness, decide, or hold. Continue through the Atlas in navigation order. Reproduce the method and verification discipline; author your own identity source and held-out evaluation material.

    The Atlas, explained

    The Repo Atlas assigns every tracked path exactly one stable file anchor. A system page explains a concept; an Atlas entry explains one file's role, contents or governed shape, readers, verification path, and related concepts. Deep entries cover authority and runbooks, standard entries cover active code and data, and compact entries cover generated, archive, or fixture material. Ignored material is described by shape without exposing a value.

    For example, scripts/waking/orient.mjs maps to file-scripts-waking-orient-mjs. Exact path search ranks that file record first. Coverage and word bands are release-verified, so an unexplained tracked file is a build failure, not an editorial footnote.

    Search and no-JS fallback

    Choose Search in the top bar or press Ctrl+K on Windows and Linux, or Command+K on macOS. Search covers headings, concepts, useful code terms, and exact repository paths. Results are generated with the site, stay on this device, and work from local files, static hosting, the gated site, and both single-file editions. Arrow keys move through results, Enter opens one, and Escape closes the dialog.

    If JavaScript is unavailable, use your browser's Find command for this page. To search the whole guide without JavaScript, open either single-file edition and use Find there. No content disappears when enhancements are unavailable.
