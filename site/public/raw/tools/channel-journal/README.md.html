# channel-journal - Telegram webhook receiver (D33, channel-recovery Tier 3)

Vercel project `edgeweaver-channel-journal` (team alan-shurafas-projects), live at
https://edgeweaver-channel-journal.vercel.app. Receives each being's Telegram updates by
webhook and appends them raw to `ew_ops.channel_journal` in the family Supabase project.
The ops machine's shim (`scripts/ops/telegram-shim.mjs`) then serves getUpdates from that
table, so messages sent while the machine is dark wait in OUR journal instead of
Telegram's 24h queue.

## Custody

- This project holds NO bot token: receiving a webhook needs none; sends stay local.
- `JOURNAL_DB_URL` = the `ew_journal_writer` role (INSERT-only on the one table).
- `WEBHOOK_SECRET_ALPHA` / `WEBHOOK_SECRET_GENESIS` validate Telegram's
  `X-Telegram-Bot-Api-Secret-Token` header; generated by
  `scripts/ops/channel-journal-setup.mjs`, stored in the repo `.env.local` and in the
  Vercel env (Sensitive/write-only, the team default; `env pull` returning empty for
  them is BY DESIGN - the D31 lesson, relearned live on 2026-07-28).
- Vercel env values must be added via stdin redirection (`cmd /c "vercel env add K
  production < file"`); PowerShell's pipe fed the CLI nothing and stored EMPTY values
  (found live 2026-07-28: pg then resolved host "base" from a mangled string).

## Endpoints

- `POST /api/webhook?being=alpha|genesis` - secret-validated insert; 500 makes Telegram
  retry, so transient DB failures delay delivery instead of losing it.
- `GET /api/health` - SELECT 1 liveness; 503 carries the pg error code, no data.

## Arming

Webhook mode is set per being by `scripts/ops/set-webhook.mjs` STRICTLY per the cutover
choreography in `runs/channel-recovery-plan.md` section 10 (Alpha first, Genesis after a
clean week). While a webhook is set, Telegram refuses getUpdates - which also ends the
stray-poller hijack class for that bot.
