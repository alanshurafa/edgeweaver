    Atlas: templates/

    TLDR

    Templates define reproducible shapes for queries, decisions, recovery, flags, night-loop contracts, local state, probes, soulfiles, and wake instructions. They are committed starting points, not live state. Operators copy or adapt them only at the named phase, keep secrets and identity outside this repository, and verify generated instances against the current schemas, gates, and authority documents.

    What this page covers

    A template makes a mechanism inspectable before it is armed. Some templates are safe to explain in detail; identity-bearing and probe-bearing shapes remain described-not-shown. Files under state are gitignored runtime instances, while these committed templates provide schema and review evidence.

    File entries

    templates/coherence-queries.sql

    schema-data
    What it is. A set of SQL sketches for computing coherence-panel signals and recovery evidence.
    What it contains. Queries and comments for relational, temporal, and recovery-oriented measures, written to be adapted to the live schema rather than executed blindly.
    Who reads it and when. Measurement engineers read it when implementing or reviewing the coherence panel.
    How to verify or reproduce it. Compare assumed tables with the current schema, run against fixture data first, inspect edge cases, and retain the distinction between an integrated tension and an unresolved contradiction. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See reproduction, loops, and operations.

    templates/decisions.md

    runbook
    What it is. The blank structure for a parent body's decision log.
    What it contains. Sections for decided matters, open gates, and signed stage advancement, preserving an append-oriented governance trail.
    Who reads it and when. A parent body or repository initializer uses it when creating a being-specific logbook.
    How to verify or reproduce it. Confirm required sections and ownership language, then test that amendments can be added without erasing prior decisions. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct. Treat any contradiction with higher-authority design as a decision-log issue, not permission to choose whichever instruction is easier.
    Related concepts. See reproduction, loops, and operations.

    templates/disaster-recovery.md

    runbook
    What it is. The machine-loss recovery runbook template.
    What it contains. A clean-machine sequence, dependency and repository restoration, encrypted backup recovery, verification, and time-to-recover recording without custody coordinates.
    Who reads it and when. Operators use it during recovery rehearsals and after an actual host loss.
    How to verify or reproduce it. Rehearse on an isolated machine, verify restored brain and repository integrity, record timing and failures, and never weaken human-governed key custody for convenience. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See reproduction, loops, and operations.

    templates/flags.default.json

    schema-data
    What it is. The committed disabled-default registry for dark-built components.
    What it contains. Component and task keys, enabled and registration states, plus the phase or gate that may authorize arming; live state is generated elsewhere and ignored.
    Who reads it and when. Initialization scripts and operators read it when rebuilding missing local flag state.
    How to verify or reproduce it. Parse the JSON, run the flag initializer, confirm new keys default to disabled, and verify existing live choices are not silently overwritten. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See reproduction, loops, and operations.

    templates/night-loop-contracts.md

    runbook
    What it is. The step-contract authority for the lite and full night loops and the separate weekly index.
    What it contains. Inputs, outputs, ordering, failure behavior, evidence expectations, scheduling boundaries, and the distinction between prepared tasks and armed tasks.
    Who reads it and when. Loop implementers, operators, and reviewers read it before changing nightly metabolism or its cadence.
    How to verify or reproduce it. Trace every script step to a contract, test failure propagation and idempotence with fixtures, keep schedules disabled until the named phase and gate, and compare emitted evidence with the operations log. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct. Treat any contradiction with higher-authority design as a decision-log issue, not permission to choose whichever instruction is easier. A clean reproduction records commands and evidence, preserves failed checks as failures, and leaves human-owned gates untouched. Keep credentials, runtime coordinates, protected identity material, and private human details outside every review artifact.
    Related concepts. See reproduction, loops, and operations.

    templates/probe-battery-starter.md

    described-not-shown
    What it is. The governed starter shape for a blinded evaluation battery.
    What it contains. Dimensions, rating and re-anchoring structure only; scenarios and protected evaluation content are deliberately not described.
    Who reads it and when. Authorized evaluators use it when a gate permits baseline or later comparison work.
    How to verify or reproduce it. Confirm blind handling and scoring protocol privately, and ensure no scenario text enters logs, this site, or canonical identity.
    Related concepts. See reproduction, loops, and operations.

    templates/soulfile-skeletons.md

    described-not-shown
    What it is. Governed structural starters for identity files that belong in a being's separate soul repository.
    What it contains. File roles and ceremony shape only; no identity themes, values, boundaries, or refusal wording are published here.
    Who reads it and when. A parent body uses the skeletons during an authorized identity-formation ceremony.
    How to verify or reproduce it. Create them only in the being's soul repository, review privately, and preserve parent-body control of canonical main.
    Related concepts. See reproduction, loops, and operations.

    templates/state-schemas.md

    schema-data
    What it is. The documented schemas for gitignored daemon-local state.
    What it contains. Shapes for audience mapping, boundaries, commitments, expectations, budget, and related operational records, using examples rather than live values.
    Who reads it and when. Runtime implementers read it when creating, migrating, or validating local state files.
    How to verify or reproduce it. Validate generated files against each documented shape, test missing and malformed fields, and confirm no runtime state becomes tracked or enters an explainer artifact. Review status language against the implementation ledger so prepared, dark, partial, pending, and live states remain distinct.
    Related concepts. See reproduction, loops, and operations.

    templates/wake-edgeweaver-genesis-SKILL.md

    described-not-shown
    What it is. A governed template for the Genesis wake skill's structure and safety boundaries.
    What it contains. Instruction shape, a pre-birth honesty guard, and a birth-gated stance transition; protected prompt material and operational coordinates stay withheld.
    Who reads it and when. Builders use it during Phase 1 proto-waking and pre-birth acceptance; it remains the waking source after birth.
    How to verify or reproduce it. Compare the installed skill with this template, run the Phase 1 wake checks, and confirm birth claims remain gated by LINEAGE entry 1.
    Related concepts. See reproduction, loops, and operations.

    templates/night-loop-lite-genesis-SKILL.md

    described-not-shown
    What it is. Installable skill template for the reconstructed Genesis lite night loop.
    What it contains. It limits execution to consolidation, diary, and provisional autobiography; requires deterministic orientation and live health; preserves evidence and audience rules; and forbids simulation, backdating, direct database writes, and protected gates content.
    Who reads it and when. Runtime operators install it only after the host preflight; reviewers inspect reconstruction provenance first.
    How to verify or reproduce it. Extract the fenced payload exactly, compare its commands with the adapter, and run the hermetic verifier before installation.
    Related concepts. See night loops and runtime handoff.
